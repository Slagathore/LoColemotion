# BR10 Reachable Catch Certification Operator

Status: promotion-family operator contract; not a milestone decision.

This document defines the only supported BR10 certification run for the exact
scaffold-constrained planar reachable new-contact catch claim. It does not
accept the milestone, admit encyclopedia knowledge, or authorize creature
guidance.

## Fixed campaign

The source contract is
`data/lab/campaigns/BR10_reachable_catch_promotion_campaign_v1.json`. The
operator refuses a dirty worktree, a source-commit change during the campaign,
a mutated BR1 inventory, any missing declared source byte, a rewritten claim
boundary, a missing program, or changed role accounting.

| Role | Programs | Assertions per replicate | Two-replicate assertions |
|---|---:|---:|---:|
| Milestone: BR10.0-BR10.3 | 4 | 56 | 112 |
| Integrity: BR10.4 | 1 | 35 | 70 |
| Total | 5 | 91 | 182 |

Every program runs twice. Each replicate receives a fresh Godot target process
inside the existing process-containment host. All ten declared bundles are
retained and reconciled; best-run selection is forbidden.

## Certified cells

`BR10.0` certifies deterministic reachable-catch planning only. Candidate
selection remains a plan, not a contact observation. Collision, timing,
mutation, non-BRACE, old-contact, and assistance boundaries remain hard
failures.

`BR10.1` certifies observed contact-phase authority only. Target arrival cannot
create contact. The accepted phase order is `SEARCH -> TOUCH -> LOAD ->
BEARING`; bearing needs the complete declared dwell, and observed loss revokes
it immediately. The local normal-load witness is not generalized per-foot
allocation.

`BR10.2` certifies the strict sagittal tangent/normal J-transpose map only.
The vertical-only accepted map remains unchanged and rejects tangent force.
The sagittal result is a commanded-force mapping, not a force sensor.

`BR10.3` certifies the paired live Godot/Jolt result only. Both worlds retain
the inherited unpowered BR7 sagittal guide and passive hinges. At the declared
disturbance the left distal contact is bearing and the right distal sphere is
unloaded and clear. A preparation-only root freeze is released with the one
declared pitch impulse. The active world plans on the first following
observation, creates ordered new `TOUCH`, `LOAD`, and `BEARING` evidence,
expands the support interval, and returns to the declared stance dwell through
the full horizon. The no-catch world receives the matched disturbance and
reaches only a late high-speed crash contact without a stance return.

`BR10.4` is integrity-only. It may reject weakened evidence but cannot replace
any of the four milestone cells.

## Running the campaign

From PowerShell in the repository root:

```powershell
& .\scripts\run_br10_reachable_catch_certification.ps1
```

The operator:

1. proves that the repository is on one clean commit;
2. validates the fixed campaign and BR1 inventory guard;
3. inventories the exact declared source closure;
4. runs the five programs twice in ten fresh target processes;
5. packages raw logs, metrics, capsules, manifests, checksums, and detached
   production bundle receipts;
6. reconciles both replicates of every program without cherry-picking;
7. writes the certification report;
8. creates a detached BR10 report-domain receipt;
9. independently reads every bundle and source inventory back; and
10. proves the repository still names the same clean commit.

On success, the console must report:

- 5/5 programs;
- 10/10 bundles;
- 182/182 assertions;
- 112/112 milestone assertions;
- 70/70 integrity assertions;
- zero failed assertions, timeouts, or unexpected engine errors; and
- one valid detached receipt for every bundle plus one detached report receipt.

The session root contains:

- `br10_certification_report.json`;
- `br10_certification_report.receipt.json`;
- the exact source inventory;
- one operator transcript; and
- ten complete bundle directories.

## Fail-closed conditions

Certification stops if any source byte, campaign field, test identity,
assertion count, ordered assertion label, process boundary, receipt, checksum,
or final readback differs from the fixed contract. It also stops if any
declared run is omitted, if the source becomes dirty, or if a report attempts
to relabel commands as measured contact loads.

## What a passing report means

A passing report can support a later human decision only for this exact
boundary:

> BR10 paired reachable new-contact catch step on the exact inherited BR7
> sagittal scaffold, with one initially bearing distal contact, one initially
> unloaded catch limb, first-observation deterministic planning, observed
> `TOUCH -> LOAD -> BEARING`, bounded finite paired actuation, support-interval
> expansion, a full-horizon stance return, and a matched no-catch crash
> control.

It does not establish per-foot measured load allocation, free-3D standing or
bracing, a general articulated load-bearing limb, generalized fall arrest,
getting up, gait, walking, creature repair, accepted encyclopedia knowledge,
or automatic creature guidance.

Certification and acceptance remain different operations. A passing report is
immutable evidence for review; it is not itself a milestone decision.
